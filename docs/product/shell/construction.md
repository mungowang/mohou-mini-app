# Construction

Layer: [Shell](README.md). Index: [features.md](../features.md).

- Owner: Shell.
- Input: the runtime root (default `~/.mini-app/runtime`), an optional port override, and the set of runtime providers Shell knows how to construct. `echo` is always in that set.
- Order: resolve the root; bootstrap `host.json` when missing; refuse a present corrupt file; construct the selected runtime provider; inject it into Host capabilities together with platform bash, push, MCP client, credentials, and config; start Host HTTP; open the panel against that origin.
- Output: one Host, one panel window, one authoring token at `authoring.token` (created if missing, not world-readable, not inside `host.json`).
- Credentials: Shell passes source specs into one provider, read and write on the same interface. The default entry is the credentials file in the mini-app home. A missing file is an empty list. Another source is another entry, with its own target; opening another kind is what a system keychain would take, and no caller changes.
- Window: the Tauri binary from **`packages/launcher/tauri`**, not from the shell npm package. It exposes no Tauri commands to the page. `pnpm dev:host` passes the loopback origin; the binary refuses any other URL. The macOS app executable is that binary. Windows `run.cmd` execs `Mohou.exe`. Paths it hands the sidecar are plain: canonicalizing yields a verbatim path on Windows, which Node's module loader cannot resolve. The processes it starts are given no console window on Windows, the sidecar included, so the panel window is the only window a launch shows and the only one whose close ends the app. A link the panel sends outside this origin goes to the system's own handler — `open` on macOS, `ShellExecuteW` on Windows, which is not a console program and does not read the URL as command-line text. A release zip places that executable beside `Resources/prefix`, so runtime data uses the user profile, as the macOS app does. A local prefix beside the executable stays the local-app layout. It spawns the shell sidecar, reads the loopback origin the sidecar prints, and opens that origin. The splash names the step in progress. It is an app asset, which Tauri serves as `tauri://localhost` on macOS and as `http://tauri.localhost` on Windows; the pre-origin guard admits that origin by name, so the splash appears on both. A remembered shell PATH starts the sidecar without waiting for the login shell, and the next open uses a PATH refreshed in the background; a remembered PATH without Node asks the shell again. The login shell is a macOS bundle concern: a Windows launch inherits the machine and user PATH, which is where Node was installed. Sidecar exit 75 starts the sidecar again and keeps the window. It does not link Pi peers before the spawn. Pi registers after the sidecar starts.
- Pending update: `update.json` names the `version` it installs and installs only after sidecar exit 75 in this process. A file left by a previous process does not install and does not block open. The install omits peer dependencies so optional Pi peers are not fetched. A tarball install also passes `--prefer-offline`, so it does not revalidate the registry. A registry install does not. A UI import that is only a peer, such as `react-is`, is a direct dependency of the kit. It stops after its budget, on failure, or when the window closes, then restores the prefix manifest and starts the sidecar from the installed prefix. The file does not stay pending. Every attempt ends with one record at `update-result.json` in the runtime root: the state, a closed reason code, the version it started from and the one it aimed at, whether it rolled back, the installer's exit code, the log path, and epoch milliseconds. The panel reads that record and acknowledges it once through `POST /api/updates/ack`; Host drops the acknowledged record, so one attempt is reported once.
- Log: every launch writes `launcher.log` in the runtime root, replacing the previous launch's file: the platform and version, the runtime root, the resolved Node, the entry, the PATH, every line the sidecar prints on stdout or stderr, and each message the launcher shows. A fatal launch shows that message natively, on macOS and on Windows, and names the log. Nothing about a failed launch is silent, and nothing about it is macOS-only.
- Failure: bad config, unknown provider id, provider `start` failure, or a missing window binary exits non-zero and prints the message. A sidecar that stops before it prints an origin, or that does not print one in time, names its exit code, the last lines it printed, and the log path. Shell does not start a half-configured Host. Port in use fails start with that message. A missing binary names `pnpm build:window`.
- Non-goals: Panel calling the constructor; Host choosing the provider implementation; embedding this platform inside another agent product; packing Tauri sources inside `@mohou/shell`.

## Implementation


Role: composition. `bootHost` resolves the root, bootstraps or refuses config, constructs `echo` and Pi, and injects both. It injects the file credential provider — whose write side the panel editor reaches through `/api/credentials` — the Pi `mcp-adapter.json` import path, the writing-skill dest table, and the authoring-MCP dest table, then starts Host. The Pi dests are Pi 1.0's own `mcp.json` in its agent directory, written with the keys Pi documents, and the `mcp-adapter.json` a Pi running the `pi-mcp-adapter` extension still reads. A failed start disposes the session. `openPanelWindow` spawns `mini-app-window` from `packages/launcher/tauri/target`, release before debug, with the loopback origin. macOS and Windows use that binary; Windows adds `.exe`. `admitWindowOrigin` rejects a non-http URL, a non-loopback host, and a path. A missing binary throws before spawn. `pnpm dev:host` spawns the window and disposes the live host when that window exits, and on `SIGINT` or `SIGTERM`. A dev restart exits 75 and leaves that window running; the next sidecar reads `panel-window.pid` in the runtime root and disposes when that window exits. The packaged macOS executable, and the Windows local `Mohou.exe`, are that Tauri binary. It sets `MINI_APP_SUPERVISED=1`, spawns `node --import tsx` on the packaged shell entry, and opens the origin that entry prints. It pipes that process's stdout and stderr into `launcher.log`, keeps the last twenty lines, and asks for the interpreter's login-shell PATH on macOS only. Sidecar exit 75 starts that process again. A pending update runs only after that exit in this process. The launcher omits peer dependencies, bounds the install, and restores the prefix manifest when the install does not finish. `react-is` is a direct dependency, so that omit does not remove it. Closing the window signals the sidecar and the binary exits. A provider that can say why it is unhealthy answers `reason`, which is what the settings probe shows. Pi links its peers after the sidecar starts: a symlink on macOS, a directory junction on Windows, and a prefix link the install removed is repaired at the next load ([provider](../runtime/provider.md) owns that rule). `MINI_APP_RUNTIME` and `MINI_APP_HOST_PORT`, when set, choose the root and the port. `MINI_APP_PANEL`, when set, is the directory of `panel.html` and `panel.js`. `MINI_APP_WINDOW`, when set, is the window binary. They are not locked. The default root is `defaultRuntimeRoot`. The credentials file is `homeCredentialsPath`. The authoring token is created if missing and is not a field of `host.json`.
